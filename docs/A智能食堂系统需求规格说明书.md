# A智能食堂系统需求规格说明书

## 1. 引言

### 1.1 编写目的

本文档用于明确面向校园/园区的智能食堂系统的功能需求、非功能需求、数据需求、接口需求和验收标准，为系统架构设计、详细设计和测试验收提供依据。

### 1.2 项目背景

本项目拟开发一套智能食堂系统，面向校园学生、教职工、园区员工、食堂商家和系统管理员，支持用户在线浏览菜单、下单点餐、凭取餐号和取餐二维码取餐，商家在线接单备餐并叫号，食堂大屏实时展示制作中队列和待取餐队列。

系统采用微服务架构实现，后端部署在容器集群中，前端部署在云服务器中。

### 1.3 术语和缩略语

| 术语 | 含义 |
| ---- | ---- |
| 用户 | 在系统中点餐、查看订单、取餐的学生、教职工或园区员工 |
| 商家 | 入驻食堂窗口或档口的经营方，负责发布菜品、接单、备餐、出餐和叫号 |
| 管理员 | 负责系统用户、商家和系统配置维护的人员 |
| 取餐号 | 商家接单时系统生成的面向用户展示的排队编号，不作为订单唯一标识 |
| 取餐二维码 | 商家出餐时系统生成的核销凭证，每个订单唯一，核销后失效 |
| 取餐码 | 取餐二维码对应的字符串编码，用于手动输入核销 |
| 制作中队列 | 商家接单后订单所在队列，大屏展示 |
| 待取餐队列 | 商家出餐后订单所在队列，按进入待取餐时间排序展示 |
| FIFO | 先进先出，仅用于队列展示排序和用户排队位置计算，不强制出餐、叫号或核销按队首进行 |
| 游客 | 未登录用户，可正常浏览菜单，但不能加入购物车和下单 |

## 2. 系统概述

### 2.1 系统目标

- 支持用户在线浏览当前可售菜品并完成点餐，减少线下排队等待时间。
- 支持商家在线接单、备餐、出餐叫号和核销取餐，提高窗口处理效率。
- 支持食堂大屏实时显示制作中队列和待取餐队列，提升取餐秩序和信息透明度。
- 支持菜品、菜单、库存和上下架管理，减少超卖和人工统计成本。
- 保证订单、库存和队列等核心业务数据在异常场景下保持一致。

### 2.2 系统范围

**系统包含：**

- 用户注册、登录、身份认证、用户信息查询与修改。
- 手机号注册，学工号可选填写；支持密码或验证码登录。
- 游客可正常浏览菜单，但不能加入购物车、下单及之后的操作。
- 商家维护菜品、每日菜单、售卖时段、库存余量、库存预警和上下架状态。
- 用户在线下单（待支付状态，预占库存）→ 完成支付 → 等待商家接单。
- 提交订单生成待支付订单时预占库存；用户取消订单、支付超时、接单超时或商家拒绝接单时恢复库存。
- 商家接单后订单自动进入制作中状态，系统生成取餐号，大屏展示制作中队列。
- 商家制作完成点击出餐，订单进入待取餐状态，系统生成取餐二维码，自动叫号一次，大屏从制作中队列移至待取餐队列。
- 商家可对待取餐订单手动再次叫号。
- 用户凭取餐二维码到窗口核销，核销后二维码失效，订单从队列移除。
- 订单在超时、取消等场景下自动处理并释放库存。
- 管理员可在管理端修改超时时间、取餐号重置规则等业务配置。

> 系统中验证码和支付功能均采用模拟方式实现，具体模拟规则见详细设计文档。

**系统不包含：**

- 与真实银行、微信、支付宝等第三方支付系统的正式资金结算。
- 食堂硬件设备的底层驱动开发。
- 外部校园一卡通系统的深度改造。
- 原生 Android / iOS App 开发。
- 复杂会员营销、优惠券、积分商城等运营系统。

### 2.3 用户角色

| 用户角色 | 说明 |
| -------- | ---- |
| 游客 | 未登录用户，可浏览菜单，不能加入购物车及下单 |
| 普通用户 | 学生、教职工或园区员工，可注册登录、浏览菜单、下单、取消订单、查看取餐信息、凭码取餐 |
| 商家 | 食堂窗口经营者，可管理本窗口菜品、发布菜单、接单、出餐、手动叫号、核销取餐 |
| 管理员 | 可管理用户、商家、系统配置（超时时间、取餐号重置规则等） |
| 大屏终端 | 食堂展示屏，接收并展示制作中队列、叫号提示和待取餐队列 |
| 系统定时任务 | 负责处理超时订单、库存预警、取餐号重置等自动化处理 |

## 3. 业务需求

### 3.1 业务流程说明

系统核心业务流程如下：

1. 用户（或游客）进入菜单页面，系统展示当前售卖时段内可售且有库存的菜品。
2. 用户（需登录）选择菜品和数量后提交订单，系统预占库存，订单进入待支付状态。
3. 用户完成支付后订单进入等待商家接单状态；若用户取消支付，订单保留为待支付状态，库存保持预占；若用户手动取消订单或待支付超时，系统取消订单并释放预占库存。
4. 若用户支付后指定时间内商家未接单，系统自动取消订单并释放库存；商家也可主动拒绝接单。
5. 商家接单后，订单自动进入制作中状态，系统生成取餐号，并在大屏该商家窗口的制作中队列区域展示。
6. 接单后用户可取消时间窗口内（默认 1 分钟，管理员可配置），用户可取消订单；超时后不可取消。商家一经接单后不可再取消。
7. 商家完成制作后点击出餐，订单进入待取餐状态，系统生成取餐二维码，在大屏上该订单从制作中队列移至待取餐队列区域，并自动执行一次叫号（大屏端醒目提示，用户端弹窗提醒）。
8. 商家可对待取餐状态的订单进行手动再次叫号。
9. 用户到窗口出示取餐二维码，商家扫描（或手动输入取餐码）完成核销，订单变为已取餐，取餐二维码失效，订单从队列中移除。
10. 以上超时时间（支付超时、接单超时、接单后用户可取消时间窗口）和取餐号重置规则均可在管理员端进行配置。

### 3.2 业务规则

- 用户必须登录后才能加入购物车、下单、查看个人订单和取餐信息。
- 游客可正常浏览菜单，但不能进行加入购物车、下单及之后的操作。
- 商家只能管理自己所属窗口的菜品、菜单和订单。
- 管理员可以管理全部用户、商家和基础数据，并可修改业务配置。
- 用户端仅展示当前售卖时段内、已上架、库存大于 0 的菜品。
- 用户创建待支付订单时系统预占库存；订单取消、超时或商家拒绝接单时系统恢复库存。
- 菜品库存低于预警阈值时，系统应向商家端提示。
- 订单状态必须按规定流程流转，不允许跳过关键状态或非法回退。
- 用户可在待支付状态随时取消订单；在待接单状态可取消订单。订单进入制作中后，在接单后用户可取消时间窗口内（默认 1 分钟）用户可取消订单，取消后订单进入已取消状态，系统释放预占库存并从制作中队列移除；超过窗口后不可取消。商家一经接单后不可再取消订单。
- 商家超过规定时间未接单时，系统自动取消订单并释放库存；商家在待接单阶段也可主动拒绝接单。
- 取餐号在商家接单时生成，是面向用户展示的排队编号。系统内部订单编号全局唯一且永不重置。取餐号的格式规则和重置策略由管理员配置，具体规则见详细设计文档。
- 取餐二维码在商家出餐时生成，每个订单唯一，核销后立即失效，不可重复使用。
- 每个取餐窗口维护独立的制作中队列和待取餐队列。队列展示顺序以订单进入该队列的时间排序。
- 出餐、叫号、取餐不强制遵循队列排序顺序。商家可对任意制作完成的订单出餐，也可对待取餐队列中的任意订单手动叫号。
- 接口必须进行统一的身份校验和频率限制。

### 3.3 数据流说明

用户（或游客）浏览菜单时，系统返回当前可售菜品。用户提交订单后，系统校验用户身份和菜品状态，创建待支付订单并预占库存。用户完成支付后，订单进入等待接单状态。

商家接单后订单自动进入制作中状态，系统生成取餐号，并通知大屏更新制作中队列。商家出餐后订单进入待取餐状态，系统生成取餐二维码，自动执行一次叫号，通过 WebSocket 推送叫号事件和队列变更到大屏；用户端通过订单详情接口轮询获取状态并展示弹窗提醒。

订单取消、超时或取餐完成后，系统更新订单状态、库存状态和队列状态。

## 4. 功能需求

### 4.1 用户注册功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-001 |
| 功能名称 | 用户注册 |
| 使用角色 | 游客 |
| 功能描述 | 用户通过手机号注册系统账号，可选填写学工号 |
| 前置条件 | 用户未登录，手机号未被注册，填写学工号时学工号未被绑定 |
| 输入 | 手机号、学工号（可选）、验证码、密码、姓名 |
| 输出 | 注册成功信息或错误提示 |
| 优先级 | 高 |

**基本流程：**

1. 用户进入注册页面，填写手机号、验证码、密码等注册信息，可选填写学工号。
2. 系统校验手机号唯一性、学工号绑定唯一性、密码强度和验证码有效性。
3. 校验通过后，系统保存用户信息。
4. 系统返回注册成功提示。

**异常流程：**

- 手机号已存在或学工号已绑定：提示"该账号已被注册"。
- 验证码无效：提示"验证码无效"。
- 密码不符合规则：提示密码规则说明。
- 必填项为空：提示对应字段不能为空。

### 4.2 用户登录与身份认证功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-002 |
| 功能名称 | 用户登录与身份认证 |
| 使用角色 | 普通用户、商家、管理员 |
| 功能描述 | 用户可使用密码或验证码登录，登录成功后获得访问凭证 |
| 前置条件 | 用户已完成注册且账号状态正常 |
| 输入 | 手机号、密码或验证码 |
| 输出 | 登录成功信息、用户基本信息、访问凭证 |
| 优先级 | 高 |

**基本流程：**

1. 用户进入登录页面，选择密码登录或验证码登录。
2. 系统校验账号状态和凭证有效性。
3. 校验通过后，系统颁发访问凭证。
4. 系统返回凭证、用户角色和基础信息。
5. 后续受保护请求需携带有效凭证。

**异常流程：**

- 凭证无效：提示"账号或密码错误"（出于安全考虑，不区分账号不存在还是密码错误）。
- 验证码无效：提示"验证码无效"。
- 账号被禁用：提示"账号已被禁用"。
- 凭证过期：提示重新登录或使用刷新机制。

### 4.3 凭证刷新功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-003 |
| 功能名称 | 凭证刷新 |
| 使用角色 | 普通用户、商家、管理员 |

| 输入 | 刷新凭证 |
| 输出 | 新的访问凭证 |
| 优先级 | 高 |

**基本流程：**

1. 客户端携带刷新凭证调用刷新接口。
2. 系统校验刷新凭证有效性。
3. 校验通过后生成新的访问凭证。
4. 系统返回新的凭证信息。

**异常流程：**

- 刷新凭证过期：提示用户重新登录。
- 刷新凭证被注销：拒绝刷新，要求重新登录。
- 用户账号被禁用：拒绝刷新并提示账号状态异常。

| 前置条件 | 用户已登录并通过身份鉴权 |

| 输出 | 用户资料详情或修改结果 |

### 4.5 菜品管理功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-005 |
| 功能名称 | 菜品管理 |
| 使用角色 | 商家 |
| 功能描述 | 商家可新增、查询、修改和删除菜品基础信息 |
| 前置条件 | 用户具有商家权限 |
| 输入 | 菜品名称、图片、分类、价格、描述、所属窗口、库存阈值 |
| 输出 | 菜品列表、菜品详情、操作结果 |
| 优先级 | 高 |

**基本流程：**

1. 商家进入菜品管理页面，新增或编辑菜品信息。
2. 系统校验菜品名称、价格、分类和所属窗口。
3. 校验通过后保存菜品信息。
4. 菜品可被加入每日菜单并设置售卖时段。

**异常流程：**

- 菜品价格不合法：提示价格不合法。
- 菜品名称为空：提示菜品名称不能为空。
- 删除已关联订单的菜品：不物理删除，仅标记为停用或下架。

### 4.6 每日菜单发布功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-006 |
| 功能名称 | 每日菜单发布 |
| 使用角色 | 商家 |
| 功能描述 | 商家为指定窗口和售卖时段配置每日固定售卖菜品，并为每个菜品设置每日自动重置库存数量。菜单配置完成后，系统每天按照菜单项中的库存设定值自动初始化或重置当天库存，商家不需要每天重复设置库存。 |
| 前置条件 | 菜品已存在且商家拥有操作权限 |
| 输入 | 窗口、售卖时段、菜品列表、每日自动重置库存数量、库存预警阈值、上架状态。 |
| 输出 | 每日菜单详情、发布结果 |
| 优先级 | 高 |

**基本流程：**

1. 商家选择窗口和售卖时段。
2. 商家从菜品库中选择要加入每日菜单的菜品。
3. 商家为每个菜品设置每日自动重置库存数量、库存预警阈值和上架状态。
4. 系统保存每日菜单配置。
5. 系统每天按配置的库存数量自动重置菜品当天库存。
6. 用户端根据当前售卖时段、上架状态和剩余库存展示可售菜品。

**异常流程：**

- 菜品已停用：禁止加入菜单。
- 初始库存不合法：提示库存不合法。

### 4.7 菜品库存与上下架管理功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-007 |
| 功能名称 | 菜品库存与上下架管理 |
| 使用角色 | 商家、系统定时任务 |
| 功能描述 | 系统支持库存预占、取消恢复、低库存预警和菜品上下架控制 |
| 前置条件 | 菜品已加入每日菜单 |
| 输入 | 菜品库存、预警阈值、上下架状态 |
| 输出 | 当前库存、预警信息、上下架结果 |
| 优先级 | 高 |

**基本流程：**

1. 商家设置每日菜单菜品的每日自动重置库存数量和预警阈值。系统每天按设定值重置 total_stock 和 remaining_stock，并清空 reserved_stock。
2. 用户提交订单创建待支付订单时系统预占库存；订单取消、超时或商家拒绝接单时系统恢复库存。
3. 库存低于预警阈值时系统向商家提示。
4. 商家可手动将菜品上架或下架。

**异常流程：**

- 库存不足：下单失败并提示库存不足。
- 菜品已下架：用户端不展示该菜品，已提交订单按订单规则处理。
- 并发扣减冲突：系统应保证库存扣减的原子性，避免超卖。

### 4.8 在线下单与支付功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-008 |
| 功能名称 | 在线下单与支付 |
| 使用角色 | 普通用户 |
| 功能描述 | 用户选择可售菜品后提交订单，系统生成待支付订单和订单明细；用户完成支付后，订单进入待接单状态 |
| 前置条件 | 用户已登录，菜品处于可售状态且库存充足 |
| 输入 | 菜品 ID、数量、备注 |
| 输出 | 订单编号、订单状态、订单明细 |
| 优先级 | 高 |

**基本流程：**

1. 用户浏览当前可售菜单，选择菜品和数量加入购物车。
2. 用户提交订单，系统创建待支付订单，保存订单和订单明细，并预占库存。
3. 用户完成支付（采用模拟支付方式），订单进入待接单状态。
4. 若用户取消支付，订单保留为待支付状态，库存保持预占；待支付超时或用户手动取消订单时释放库存。
5. 在待支付订单详情页用户可重新发起支付（无需重新预占库存），也可取消订单。

**异常流程：**

- 菜品不可售：提示菜品当前不可购买。
- 库存不足：提示库存不足。
- 支付密码错误：提示支付密码错误。
- 库存预占失败：订单创建失败并提示稍后重试。
- 用户重复提交：系统应防止重复创建订单。

### 4.9 订单状态流转功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-009 |
| 功能名称 | 订单状态流转 |
| 使用角色 | 普通用户、商家、系统定时任务 |
| 功能描述 | 系统按业务规则维护订单从待支付到已取餐的完整状态 |
| 前置条件 | 订单已创建 |
| 输入 | 订单编号、状态变更操作 |
| 输出 | 最新订单状态 |
| 优先级 | 高 |

**订单状态：**

| 状态 | 说明 |
| ---- | ---- |
| 待支付 | 订单已创建，等待用户支付 |
| 已下单（待接单） | 用户已支付，等待商家接单 |
| 制作中 | 商家已接单，正在制作 |
| 待取餐 | 商家已出餐，等待用户取餐 |
| 已取餐 | 商家已核销，订单完结 |
| 已取消 | 订单被取消 |

**正常流程：** 待支付 → 已下单（待接单） → 制作中 → 待取餐 → 已取餐

**取消分支：** 订单在待支付、待接单或符合条件的制作中状态时可进入已取消。

**基本流程：**

1. 订单创建后状态为待支付。
2. 用户完成支付后状态变为已下单（待接单）。
3. 商家接单后自动进入制作中状态，系统生成取餐号。
4. 商家完成制作点击出餐后状态变为待取餐，系统生成取餐二维码，自动叫号一次。
5. 商家核销取餐二维码后状态变为已取餐，二维码失效。

**异常流程：**

- 非法状态变更：系统拒绝操作并提示当前状态不可执行。
- 订单不存在：提示订单不存在。
- 商家无权限操作订单：拒绝操作。
- 订单已取消或已取餐：禁止再次变更状态。

### 4.10 限时取消与自动取消功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-010 |
| 功能名称 | 限时取消与自动取消 |
| 使用角色 | 普通用户、商家、系统定时任务 |
| 功能描述 | 用户可在规定条件内取消订单；商家可拒绝接单；系统在超时场景下自动取消订单并释放库存 |
| 前置条件 | 订单处于可取消状态 |
| 输入 | 订单编号、取消原因 |
| 输出 | 订单取消结果、库存恢复结果 |
| 优先级 | 高 |

**取消规则：**

- **用户手动取消**：待支付状态随时可取消；待接单状态可取消；制作中状态（接单后用户可取消时间窗口内，默认 1 分钟）可取消；超过窗口后不可取消。取消后恢复预占库存。
- **商家拒绝接单**：商家在待接单列表中可选择拒绝接单，订单取消并释放库存。
- **自动取消**：待支付超时（默认 10 分钟）或待接单超时（默认 10 分钟）时，系统自动取消订单并释放库存。

**异常流程：**

- 订单不可取消：提示当前订单不可取消。
- 库存恢复失败：记录异常日志并触发补偿处理。
- 订单已取消：提示无需重复取消。

### 4.11 取餐排队队列功能

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-011 |
| 功能名称 | 取餐排队队列 |
| 使用角色 | 商家、普通用户、大屏终端 |
| 功能描述 | 系统为每个窗口维护独立的制作中队列和待取餐队列，队列按进入时间排序展示 |
| 前置条件 | 商家接单后订单进入制作中队列，出餐后进入待取餐队列 |
| 输入 | 窗口编号、订单编号、取餐号 |
| 输出 | 制作中队列、叫号序列、待取餐队列、排队位置 |
| 优先级 | 高 |

**基本流程：**

1. 商家接单后，订单自动进入制作中状态，系统生成取餐号，订单加入对应窗口的制作中队列。
2. 商家完成制作并点击出餐后，订单进入待取餐状态，从制作中队列移至待取餐队列。
3. 系统按订单进入待取餐状态的时间维护展示顺序。
4. 大屏实时展示制作中队列和待取餐队列。
5. 用户端可查看自己的排队状态。
6. 商家核销后订单从待取餐队列移除。

**异常流程：**

- 订单重复入队：系统应保证同一订单只存在于一个队列中。
- 窗口不存在：拒绝入队并记录异常。
- 队列数据异常时，系统应可从持久化数据恢复队列。

| 项目 | 内容 |
| ---- | ---- |
| 功能编号 | FR-012 |
| 功能名称 | 出餐自动叫号与商家手动叫号 |
| 使用角色 | 商家、大屏终端、普通用户 |
| 功能描述 | 商家出餐后系统自动对该订单叫号一次；商家也可对待取餐队列中的订单手动再次叫号。叫号时大屏端应有醒目提示，用户端应有弹窗提醒 |
| 前置条件 | 订单处于制作中（出餐）或待取餐（手动叫号） |
| 输入 | 窗口编号、订单编号、取餐号 |
| 输出 | 叫号事件、大屏推送消息、用户取餐提醒 |
| 优先级 | 高 |

**基本流程：**

1. 商家在商家端查看制作中订单队列，对制作完成的订单点击出餐。
2. 系统将该订单设置为待取餐，从制作中队列移至待取餐队列。

### 4.13 取餐二维码核销功能

| 项目 | 内容 |

| 功能名称 | 取餐二维码核销 |

| 功能描述 | 用户凭取餐二维码到窗口取餐，商家扫描二维码核销（或手动输入取餐码核销）后订单变更为已取餐，二维码立即失效 |

- 订单未到待取餐状态：提示订单暂不可取餐。

## 5. 非功能需求

### 5.1 性能需求

- 普通接口平均响应时间不超过 2 秒。
- 菜单列表、订单详情等高频查询接口平均响应时间不超过 1 秒。
- 大屏叫号消息推送延迟在正常网络条件下不超过 1 秒。
- 系统应支持不少于 300 个用户同时在线浏览菜单和查询订单。
- 高峰期应支持不少于 100 个用户并发下单。
- 库存扣减应具备并发控制能力，避免超卖。
- 系统应支持基于 IP 和用户维度的接口访问频率限制。

### 5.2 安全性需求

- 用户密码必须加密存储，不得明文保存。
- 受保护接口必须经过身份鉴权。
- 刷新凭证应支持过期、注销和失效机制。
- 不同角色只能访问其权限范围内的数据和接口。
- 商家只能访问所属窗口的数据。
- 系统应防止 SQL 注入、XSS、CSRF、越权访问和接口重放等常见风险。
- 验证码应设置有效期和发送频率限制。
- 登录失败提示不应区分账号不存在还是密码错误，避免账号枚举。
- 重要操作如登录、接单、取消订单、核销取餐、库存修改应记录操作日志。

### 5.3 可用性需求

- 用户端页面应清晰展示菜品名称、价格、库存状态、售卖时段和取餐信息。
- 用户端应提供便捷的购物车入口，支持查看和修改已选菜品。
- 商家端应突出显示新订单、待接单订单、制作中订单和待取餐队列。
- 大屏页面应适配食堂显示设备，字体清晰、队列信息易读。
- 表单输入错误时应给出明确提示。
- 用户完成下单后应能方便查看取餐号和取餐二维码。
- 实时连接断开后客户端应具备自动重连能力。

### 5.4 可靠性需求

- 系统异常时不得导致订单、库存和队列核心数据丢失。
- 订单创建、库存预占、库存释放应具备一致性保障或补偿机制。
- 队列数据异常时，应能根据持久化数据恢复队列。
- 数据库应支持定期备份。
- 微服务异常时应记录错误日志并返回友好提示。
- 核心服务应配置健康检查和自动重启策略。

### 5.5 可维护性需求

- 业务规则如取消时间、接单超时时间、库存预警阈值应配置化，可在管理员端修改。
- 接口命名、返回格式、错误码和日志格式应统一。
- 数据库表结构应具备清晰字段注释。
- 系统应输出必要的运行日志，便于排查业务问题。

### 5.6 可扩展性需求

- 用户角色和权限模型应支持扩展。
- 菜品分类、售卖时段、窗口类型应支持配置。
- 系统应支持后续新增支付、评价、通知等服务。

## 9. 约束与假设

### 9.1 开发约束

- 系统必须采用微服务架构实现。
- 系统至少拆分为用户服务、菜品与菜单服务、订单服务、取餐与排队服务、网关服务 5 个核心服务。
- 各微服务应能够独立运行、独立启动和独立扩展。
- 系统必须使用服务注册、发现和配置管理组件。
- 系统必须使用 API 网关作为统一入口。
- 系统必须支持统一的身份鉴权。
- 前端应采用 Vue 3 开发，四个端均为独立 Web 工程。
- 后端必须部署在容器集群环境中。
- 数据库建议使用 MySQL，缓存建议使用 Redis。

> 具体技术选型、架构设计和服务间通信方式见《架构设计文档》。

### 9.2 业务约束

- 用户必须登录后才能加入购物车、创建订单和查看取餐信息。
- 游客可浏览菜单但不能下单。
- 商家只处理所属窗口的订单和菜品。
- 用户端仅展示当前可售菜品。
- 订单操作必须满足状态规则。
- 取餐号在商家接单时生成，是展示编号；系统内部订单编号全局唯一。
- 取餐二维码在商家出餐时生成，核销后立即失效。
- 出餐、叫号、取餐不强制遵循队列排序顺序。
- 库存必须在创建待支付订单时预占，在订单取消、超时或商家拒绝接单时恢复。

### 9.3 数据约束

- 手机号和学工号在用户表中应保持唯一。
- 用户密码必须存储加密摘要。
- 菜品价格不能小于 0。
- 菜品库存不能小于 0。
- 订单编号全局唯一。
- 取餐码必须唯一且只能核销一次。
- 订单状态只能在合法状态集合中流转。
- 同一订单不能重复加入同一窗口队列。
- 删除用户、商家、菜品时不得直接删除历史订单数据，应采用状态标记或逻辑删除。

### 9.4 假设条件

- 用户具备基本网页操作能力。
- 校园或园区网络能够支持系统正常访问。
- 食堂商家具备平板等浏览器访问设备。
- 商家平板浏览器支持调用摄像头进行扫码。
- 大屏终端可通过浏览器访问系统页面。
- 课程项目中短信、支付、文件存储等外部接口可采用模拟实现。
- 容器集群、数据库、缓存和注册中心在部署前已准备完毕。
- 云服务器已配置好前端部署环境。

## 10. 验收标准

| 验收项 | 验收标准 |
| ------ | -------- |
| 微服务拆分 | 至少包含用户服务、菜品与菜单服务、订单服务、取餐与排队服务、网关服务，服务可独立运行 |
| 服务注册与发现 | 各微服务能够成功注册到注册中心，网关可通过服务发现转发请求 |
| 网关路由 | API 请求统一通过网关进入，并能正确路由到目标服务 |
| 前端多端 | 用户端、商家端、管理员端和大屏端页面均可独立访问 |
| 身份鉴权 | 登录成功后获得访问凭证，未携带或携带无效凭证访问受保护接口会被拒绝 |
| 用户注册登录 | 支持手机号注册、学工号可选填写，支持密码或验证码登录 |
| 凭证刷新 | 刷新凭证有效时可换取新的访问凭证 |
| 游客浏览 | 未登录用户可正常浏览菜单，但不能加入购物车和下单 |
| 菜品管理 | 商家能够新增、查询、修改、删除或停用菜品 |
| 每日菜单 | 能够按日期和售卖时段发布菜单，用户端仅展示当前可售菜品 |
| 购物车 | 用户端应提供购物车入口，支持查看和修改已选菜品 |
| 下单与支付 | 用户可提交订单并完成支付；可取消支付保留待支付状态；待支付订单可重新发起支付 |
| 库存预占与恢复 | 提交订单创建待支付订单时预占库存；订单取消、支付超时、接单超时或商家拒绝接单时恢复库存 |
| 库存预警 | 库存低于阈值时商家端能够看到预警 |
| 订单状态流转 | 正常流程：待支付→已下单（待接单）→制作中→待取餐→已取餐；取消分支进入已取消 |
| 取餐号 | 接单时生成，是面向用户展示的排队编号；系统内部订单编号全局唯一 |
| 取餐二维码 | 出餐时生成，核销后立即失效 |
| 限时取消 | 待支付状态可随时取消；待接单状态可取消；制作中状态在窗口内可取消 |
| 商家拒绝接单 | 商家可主动拒绝接单，订单取消并释放库存 |
| 自动取消 | 支付超时或商家超时未接单时订单自动取消并释放库存 |
| 制作中队列 | 每个窗口维护制作中订单队列，大屏实时展示 |
| 待取餐队列 | 每个窗口维护待取餐队列，按进入时间排序展示 |
| 出餐自动叫号 | 商家出餐后系统自动叫号一次，大屏收到 WebSocket 推送提醒，用户端通过轮询获取提醒 |
| 手动叫号 | 商家可对待取餐队列中任意订单手动叫号 |
| 取餐核销 | 商家扫描取餐二维码完成核销，可通过手动输入取餐码核销 |
| 大屏显示 | 大屏实时显示制作中队列、叫号提示和待取餐队列，断线后可重连或刷新恢复 |
| 管理员配置 | 管理员可在管理端修改超时时间、取餐号重置规则等业务配置 |
| 接口限流 | 系统支持 IP 级和用户级接口访问频率限制 |
| 容器部署 | 后端核心微服务能够以容器形式部署到集群，并具备基础健康检查 |

### 12.2 业务流程图信息说明

主要节点如下：

1. 用户（或游客）浏览当前可售菜单。
2. 用户（需登录）选择菜品加入购物车，提交订单 → 创建待支付订单并预占库存。
3. 用户完成支付 → 订单进入待接单状态；取消支付 → 订单保留待支付，可重新发起支付（无需重新预占库存）。
4. 待支付超时自动取消并释放库存；用户也可手动取消。
5. 商家查看待接单订单，选择接单或拒绝接单。
6. 接单 → 订单进入制作中，系统生成取餐号，加入大屏制作中队列。
7. 拒绝接单 → 订单取消，释放库存。
8. 超时未接单 → 系统自动取消，释放库存。
9. 商家完成制作点击出餐 → 订单进入待取餐，生成取餐二维码，移至大屏待取餐队列，自动叫号一次。
10. 商家可对待取餐订单手动再次叫号。
11. 用户到窗口展示取餐二维码，商家扫描（或手动输入）核销成功。
12. 订单变更为已取餐，取餐二维码失效，从队列移除。

### 12.3 订单状态说明

| 状态 | 说明 |
| ---- | ---- |
| 待支付 | 订单已创建，等待用户支付 |
| 已下单（待接单） | 用户已支付，等待商家接单 |
| 制作中 | 商家已接单，正在制作 |
| 待取餐 | 商家已出餐，等待用户取餐 |
| 已取餐 | 商家已核销，订单完结 |
| 已取消 | 订单被取消 |

**正常流程：** 待支付 → 已下单（待接单） → 制作中 → 待取餐 → 已取餐

**取消分支：** 待支付 / 待接单 / 符合条件的制作中 → 已取消

完整状态转换规则见《详细设计文档》。

### 12.4 数据流图信息说明

外部实体：

- 用户端（手机）
- 商家端（平板）
- 管理端（PC）
- 大屏终端

处理过程：

- P1 用户认证处理
- P2 菜品与菜单管理
- P3 订单创建与状态处理
- P4 库存预占与恢复处理
- P5 取餐排队与叫号处理
- P6 鉴权、路由与限流处理

数据存储：

- D1 用户库
- D2 菜品与菜单库
- D3 库存库
- D4 订单库
- D5 队列库（制作中队列 + 待取餐队列）
- D6 取餐号序列存储
- D7 操作日志库
- D8 系统配置库

主要数据流：

- 用户端/游客端向 P2 请求当前菜单，P2 查询 D2 和 D3 后返回可售菜品。
- 用户端向 P1 提交登录信息，P1 查询 D1 后返回访问凭证。
- 用户端向 P3 提交订单，P3 调用 P4 预占库存并写入 D4；用户完成支付后，P3 更新订单为待接单状态。
- 商家端向 P3 提交接单/不接单/出餐状态变更。
- P3 在商家接单后通知 P5，P5 生成取餐号并加入制作中队列。
- P3 在商家出餐后通知 P5，P5 生成取餐二维码、移至待取餐队列、自动叫号一次。
- 商家端可向 P5 发起手动叫号和核销。
- P5 更新 D5，并向大屏终端推送队列数据。
- 管理员端可修改 D8 中的系统配置项。
- P6 位于所有客户端和业务服务之间，承担鉴权、限流和路由。
