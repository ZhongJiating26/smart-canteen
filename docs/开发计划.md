# 二、第 0 阶段：项目准备

## 0.1 固定开发范围

先不要一上来写代码。先把本次课程项目的**最低可交付范围**固定下来。

你的最低可交付范围应该是：

1. 用户注册、登录、JWT 鉴权。
2. 商家菜品管理、每日菜单、库存。
3. 用户浏览菜单、下单、支付。
4. 商家接单、拒单、出餐。
5. 取餐号、二维码、核销。
6. 大屏 WebSocket 展示制作中队列和待取餐队列。
7. RocketMQ 处理支付超时、接单超时。
8. Seata 保证创建订单和库存预占一致。
9. K3S 部署后端服务。
10. 四个前端端口可访问。

需求文档中已经明确：系统至少拆分为用户服务、菜品与菜单服务、订单服务、取餐与排队服务、网关服务 5 个核心服务，前端采用 Vue 3，后端部署在容器集群中，必须有服务注册发现、API 网关和统一鉴权。

```text

- Redis
- Nacos
- RocketMQ NameServer
- RocketMQ Broker
- RocketMQ Dashboard
- Seata Server
```

建议目录：

```text
deploy/docker-compose/
├── docker-compose.yml
├── mysql/
├── nacos/
├── rocketmq/
├── seata/
└── redis/
```

本阶段目标：

```text
1. MySQL 可以连接。
2. Redis 可以连接。
3. Nacos 控制台可以打开。
```

推荐启动顺序：

```text

正式部署前置检查顺序：
部署 MySQL 并确认可访问 → 部署 Nacos → 部署 Redis → 部署 RocketMQ → 部署 Seata Server
→ 部署 User Service → Menu Service → Pickup Service → Order Service → Gateway → 前端
```

你的正式部署启动顺序设计为：MySQL → Redis → Nacos → RocketMQ → Seata Server → User Service → Menu Service → Pickup Service → Order Service → Gateway → 前端。开发阶段可以先按“数据库和注册中心优先”的原则执行。

# 四、第 2 阶段：数据库和基础配置

## 2.1 创建数据库

先创建 4 个业务库：

```sql

CREATE DATABASE canteen_menu DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

各服务应独占数据库，只能通过 API 或 OpenFeign 协作，不能跨库直接查别的服务数据。这一点在你的架构文档中已经确定。

# 七、第 5 阶段：后端服务编码顺序

推荐编码顺序：

```text
user-service
→ menu-service
→ pickup-service
→ order-service
→ gateway-service 鉴权完善
→ Seata
→ RocketMQ
→ WebSocket
```

原因：

```text
order-service 依赖 user-service 验证支付密码；
order-service 依赖 menu-service 预占/恢复库存；
order-service 依赖 pickup-service 入队/出队/生成取餐码；
gateway-service 依赖 user-service 颁发出来的 JWT 才能完整验证。
```

## 5.1 user-service 开发

### 第一步：实体和 Mapper

实现：

```text
User
LoginLog
RefreshToken
UserMapper
LoginLogMapper
RefreshTokenMapper
```

### 第二步：注册

接口：

```text
POST /api/user/register
```

实现逻辑：

```text
1. 校验 username 是否存在。
2. 校验验证码。
3. BCrypt 加密登录密码。
4. payPassword 按课程模拟要求保存。
5. 插入 user。
6. 写登录/操作日志。
```

### 第三步：验证码

接口：

```text
POST /api/user/send-code
```

逻辑：

```text
1. 验证手机号格式。
2. Redis 写入 sms:{phone} = 123456，TTL 5 分钟。
3. Redis 写入 sms:limit:{phone}，限制 60 秒重复发送。
```

### 第四步：密码登录

接口：

```text
POST /api/user/login/password
```

逻辑：

```text
1. 查 user。
2. 校验密码。
3. 校验 status。
4. 生成 access_token 和 refresh_token。
5. refresh_token 写 DB。
6. token:refresh:{userId} 写 Redis。
7. 返回 token 和 userInfo。
```

### 第五步：验证码登录

接口：

```text
POST /api/user/login/code
```

逻辑类似密码登录，只是凭证校验改成 Redis 验证码。

### 第六步：刷新 Token

接口：

```text
POST /api/user/refresh
```

逻辑：

```text
1. 校验 refresh_token。
2. 校验 DB 中 refresh_token 是否有效。
3. 旧 access_token jti 加入 Redis 黑名单。
4. 旧 refresh_token 标记失效。
5. 生成新的双 Token。
```

### 第七步：支付密码验证

接口：

```text
POST /api/user/verify-pay-password
```

这是给 order-service 调用的 Feign 内部接口。

实现：

```text
1. 检查 pay_lock:{userId} 是否存在。
2. 对比 pay_password。
3. 错误则 INCR pay_error:{userId}。
4. 错 5 次则锁定 30 分钟。
5. 正确则删除错误计数。
```

### user-service 完成标准

```text
1. 注册成功。
2. 重复注册返回错误。
3. 密码登录成功。
4. 密码错误返回错误。
5. Token 刷新成功。
6. 支付密码错误 5 次锁定。
7. Knife4j 能看到接口。
```

## 5.2 menu-service 开发

### 第一步：基础表 CRUD

先做最简单的：

```text
商家 merchant
窗口 stall
分类 dish_category
菜品 dish
```

接口：

```text
GET /api/menu/categories
POST /api/menu/categories
GET /api/menu/dishes
POST /api/menu/dishes
PUT /api/menu/dishes/{dishId}
DELETE /api/menu/dishes/{dishId}
```

### 第二步：每日菜单

接口：

```text
POST /api/menu/daily-menus
GET /api/menu/daily-menus
PUT /api/menu/daily-menus/{menuId}/items
```

实现：

```text
1. 选择日期。
2. 选择售卖时段。
3. 选择窗口。
4. 选择菜品。
5. 设置 total_stock、remaining_stock、reserved_stock、alert_threshold。
```

### 第三步：用户可售菜单

接口：

```text
GET /api/menu/available
```

过滤逻辑：

```text
1. 当前日期匹配 menu_date。
2. 当前时间匹配 meal_period。
3. is_listed = 1。
4. remaining_stock > 0。
5. dish.status = 1。
```

### 第四步：库存预占接口

Feign 内部接口：

```text
POST /api/menu/inventory/reserve
```

核心 SQL：

```sql
UPDATE daily_menu_item
SET reserved_stock = reserved_stock + ?,
    remaining_stock = remaining_stock - ?
WHERE id = ?
  AND remaining_stock >= ?;
```

如果影响行数是 0，说明库存不足，抛 `INVALID_STOCK`。

### 第五步：库存恢复接口

Feign 内部接口：

```text
POST /api/menu/inventory/release
```

注意必须幂等。

建议用 `inventory_log` 判断：

```text
order_id + change_type = RELEASE 是否已经存在
```

存在则直接返回成功。

### 第六步：库存确认消费接口

Feign 内部接口：

```text
POST /api/menu/inventory/consume
```

核销完成后调用：

```text
reserved_stock - quantity
```

也要幂等：

```text
order_id + change_type = CONSUME
```

### menu-service 完成标准

```text
1. 商家能新增菜品。
2. 商家能发布当天菜单。
3. 用户能看到可售菜单。
4. 库存不足时预占失败。
5. 取消订单后库存能恢复。
6. 核销后 reserved_stock 能减少。
```

## 5.3 pickup-service 开发

这个服务不要等 order-service 写完才开始。先独立用测试接口模拟订单入队。

### 第一步：取餐号生成

实现：

```text
pickup_number_sequence
```

规则：

```text
A001 → A002 → ... → A999 → B001 → ... → Z999 → A001
```

注意：

```text
1. 所有窗口共享全局序列。
2. 接单时生成取餐号。
3. 已取消订单的取餐号不回收。
4. 用 Redis 分布式锁 lock:pickup_seq 防并发。
```

### 第二步：制作中队列

内部接口：

```text
POST /api/pickup/internal/enqueue-preparing
```

逻辑：

```text
1. 检查 order_id 是否已经入队。
2. 生成或返回已有 pickupNo。
3. 插入 preparing_queue_item。
4. 更新 Redis queue:preparing:{stallId}。
5. 推送 WebSocket PREPARING_UPDATE。
```

### 第三步：待取餐队列

内部接口：

```text
POST /api/pickup/internal/enqueue-waiting
```

逻辑：

```text
1. 检查 order_id 是否已经有二维码。
2. 生成 pickup_code。
3. 生成 qrcode_content。
4. 从 preparing_queue_item 删除。
5. 插入 waiting_queue_item。
6. 插入 call_event，call_type = AUTO。
7. 更新 Redis 队列。
8. 推送 WAITING_UPDATE 和 CALL_NOTIFY。
```

### 第四步：移除队列

内部接口：

```text
POST /api/pickup/internal/remove-queue
```

用于订单取消。

逻辑：

```text
1. 从 preparing_queue_item 删除。
2. 从 waiting_queue_item 删除。
3. 刷新 Redis。
4. 推送队列更新。
```

### 第五步：队列查询

公开接口：

```text
GET /api/pickup/preparing/{stallId}
GET /api/pickup/waiting/{stallId}
GET /api/pickup/snapshot/{stallId}
```

读取逻辑：

```text
1. 优先查 Redis。
2. Redis 没有则查 MySQL。
3. 查 MySQL 后重建 Redis。
```

### 第六步：手动叫号

接口：

```text
POST /api/pickup/call
```

逻辑：

```text
1. 校验订单在 waiting_queue_item 中。
2. 插入 call_event，call_type = MANUAL。
3. 推送 CALL_NOTIFY。
```

### 第七步：核销

接口：

```text
POST /api/pickup/verify
```

逻辑：

```text
1. 支持扫码 qrcodeContent。
2. 支持手动 pickupCode。
3. 校验二维码存在。
4. 校验未核销。
5. 校验窗口匹配。
6. 调 order-service 内部接口把订单改为 COMPLETED。
7. 删除 waiting_queue_item。
8. 标记二维码已核销。
9. 插入 verify_record。
10. 推送队列更新。
```

### pickup-service 完成标准

```text
1. 取餐号递增正确。
2. 同一订单不能重复入队。
3. 出餐后能从制作中移到待取餐。
4. 自动叫号有 call_event。
5. 手动叫号有 call_event。
6. 核销后二维码失效。
7. Redis 清空后能从 MySQL 恢复队列。
```

队列、取餐二维码、核销和大屏恢复都是你的核心验收点，需求中明确要求取餐二维码唯一且核销后失效，队列异常时能从持久化数据恢复。

## 5.4 order-service 开发

order-service 是最复杂的，必须最后写核心流程，因为它依赖 user、menu、pickup。

### 第一步：订单基础查询

先实现：

```text
GET /api/order/my
GET /api/order/{orderId}
GET /api/order/{orderId}/status
GET /api/order/merchant/list
```

此时可以先用测试数据验证查询。

### 第二步：创建订单

接口：

```text
POST /api/order/create
```

请求头：

```text
X-Idempotent-Key: UUID
```

逻辑：

```text
1. 校验用户角色 USER。
2. 校验幂等 key。
3. 调 menu-service 查询菜品快照和库存。
4. 计算总金额。
5. 开启 Seata 全局事务。
6. 插入订单主表，状态 PENDING_PAY。
7. 插入订单明细。
8. 调 menu-service 预占库存。
9. 提交事务。
10. 写 Redis 幂等 key。
11. 发送 RocketMQ pay_timeout 延迟消息。
```

### 第三步：支付订单

接口：

```text
POST /api/order/{orderId}/pay
```

逻辑：

```text
1. 校验订单存在。
2. 校验订单属于当前用户。
3. 校验状态 PENDING_PAY。
4. 判断是否支付超时。
5. 调 user-service 验证支付密码。
6. 更新订单状态为 PAID。
7. 写 order_status_log。
8. 发送 RocketMQ accept_timeout 延迟消息。
```

### 第四步：取消订单

接口：

```text
POST /api/order/{orderId}/cancel
```

支持：

```text
PENDING_PAY 可取消
PAID 可取消
PREPARING 在接单后 1 分钟内可取消
READY / COMPLETED / CANCELLED 不可取消
```

逻辑：

```text
1. 校验订单归属。
2. 校验状态是否可取消。
3. 更新订单为 CANCELLED。
4. 调 menu-service release 库存。
5. 调 pickup-service remove-queue。
6. 写状态日志。
```

### 第五步：商家接单

接口：

```text
POST /api/order/{orderId}/accept
```

逻辑：

```text
1. 校验角色 MERCHANT。
2. 校验订单状态 PAID。
3. 校验商家只能处理自己窗口订单。
4. 判断是否接单超时。
5. 更新订单状态 PREPARING。
6. 调 pickup-service enqueue-preparing。
7. 回写 pickup_no。
8. 写状态日志。
```

### 第六步：商家拒绝接单

接口：

```text
POST /api/order/{orderId}/reject
```

逻辑：

```text
1. 状态必须是 PAID。
2. 更新 CANCELLED。
3. 调 menu-service release。
4. 写状态日志。
```

### 第七步：商家出餐

接口：

```text
POST /api/order/{orderId}/dispatch
```

逻辑：

```text
1. 状态必须是 PREPARING。
2. 更新 READY。
3. 调 pickup-service enqueue-waiting。
4. 回写 pickup_qrcode_id。
5. 写状态日志。
```

### 第八步：核销状态同步内部接口

接口：

```text
PUT /api/order/internal/{orderId}/status
```

由 pickup-service 调用。

逻辑：

```text
1. 校验当前状态 READY。
2. 更新 COMPLETED。
3. 调 menu-service consume 库存。
4. 写状态日志。
```

### order-service 完成标准

```text
1. 用户能创建订单并预占库存。
2. 支付后状态变 PAID。
3. 商家接单后生成取餐号。
4. 出餐后生成二维码并自动叫号。
5. 核销后订单 COMPLETED。
6. 取消、拒单、超时都能释放库存。
7. 重复请求不会重复创建订单。
```

你的需求流程中，完整链路是：浏览菜单 → 提交订单并预占库存 → 支付 → 商家接单 → 生成取餐号 → 出餐 → 生成二维码并自动叫号 → 核销 → 订单完成。

## 5.5 gateway-service 开发

网关建议分两步做：先路由，后鉴权。

### 第一步：基础路由

配置路由：

```text
/api/user/**      → user-service
/api/menu/**      → menu-service
/api/order/**     → order-service
/api/pickup/**    → pickup-service
/api/admin/**     → 按路径转发到对应服务
/ws/**            → pickup-service WebSocket
```

### 第二步：白名单

白名单：

```text
/api/user/register
/api/user/send-code
/api/user/login/**
/api/user/refresh
/api/menu/available
/api/pickup/preparing/**
/api/pickup/waiting/**
/api/pickup/snapshot/**
/ws/**
```

### 第三步：JWT 鉴权

实现 `AuthGlobalFilter`：

```text
1. 读取 Authorization。
2. 校验 Bearer token。
3. 校验签名。
4. 校验过期。
5. 检查 Redis token:blacklist:{jti}。
6. 解析 userId、role、username。
7. 注入 X-User-Id、X-User-Role、X-Username。
```

### 第四步：角色拦截

实现 `RoleRouteFilter`：

```text
/api/admin/** 只能 ADMIN
/api/order/create 只能 USER
/api/order/{id}/pay 只能 USER
/api/order/merchant/** 只能 MERCHANT
/api/menu/dishes POST/PUT/DELETE 只能 MERCHANT
/api/pickup/call 只能 MERCHANT
/api/pickup/verify 只能 MERCHANT
```

### 第五步：限流

实现 Redis + Lua 限流：

```text
IP 级：100 req/s
用户级：50 req/s
敏感接口：5 req/min
```

### gateway-service 完成标准

```text
1. 所有请求都必须经过 gateway。
2. 未登录访问受保护接口返回 401。
3. 角色不匹配返回 403。
4. 登录、注册、菜单浏览可以公开访问。
5. WebSocket 能通过 /ws/** 转发。
```

```text

tag = accept_timeout
delay = 10min
```

### 第五步：消费者实现

消费逻辑：

```text
1. 收到 pay_timeout。
2. 查订单。
3. 如果订单仍是 PENDING_PAY，并且确实超过 pay_timeout_minutes，则取消并释放库存。
4. 否则忽略。

1. 收到 accept_timeout。
2. 查订单。
3. 如果订单仍是 PAID，并且确实超过 accept_timeout_minutes，则取消并释放库存。
4. 否则忽略。
```

### 第六步：补一个定时扫描兜底

即使有 RocketMQ，也建议保留定时任务：

```text

```

原因：演示时如果 RocketMQ 没及时触发，定时扫描能兜底。

```text
1. 不要让它随意改数据库字段。
2. 不要让它跨服务直接查库。
3. 不要让它绕过网关鉴权。
4. 不要让它把 Token、密码、取餐码写进日志。
5. 不要让它一次生成所有微服务。
6. 不要让它把模拟支付写成真实支付。
```

详细设计也要求重要操作记录日志，但日志中不得保存明文密码、完整 Token、完整取餐码等敏感信息。

# 十五、最重要的开发建议

不要从订单服务开始写。正确顺序是：

```text
基础组件 → 数据库 → common → user → menu → pickup → order → gateway 完善 → RocketMQ / Seata 深化 → 前端 → 测试 → 部署
```

其中最容易出问题的是：

```text
1. Seata 事务回滚。
2. RocketMQ 延迟消息。
3. 订单状态并发更新。
4. 库存预占和恢复幂等。
5. 队列重复入队。
6. 网关路径和角色拦截。
7. WebSocket 通过网关转发。
8. K3S 中服务互相访问地址配置。
```

开发时每完成一个接口，就马上写测试、用 Apifox 验证、提交 Git。不要等所有服务写完再联调。
