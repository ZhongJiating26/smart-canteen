# 智能食堂系统项目答辩与面试问答资料

> 说明：本文根据当前仓库中的实际代码、SQL、部署清单和测试目录整理。回答时不要机械背诵，可以先给结论，再根据老师或面试官的追问展开。对于当前仍属于教学演示实现的部分，应如实说明边界和生产化改进方案。

## 一、项目介绍

问：请你先用一两分钟介绍一下这个项目。

答：这是一个面向校园或园区食堂的智能点餐与取餐系统，解决传统食堂排队点餐、窗口拥堵、出餐信息不透明的问题。系统覆盖用户浏览菜单、加入购物车、创建订单、模拟支付、商家接单、制作出餐、自动叫号、二维码核销取餐的完整闭环。

系统采用前后端分离和微服务架构。前端使用 Vue 3、Vite、Vue Router、Pinia 和 Axios，提供用户端、商家端、管理端和大屏端四个入口。后端使用 Java 17、Spring Boot 3.3.5、Spring Cloud Gateway、Nacos、MyBatis-Plus、MySQL、Redis、RocketMQ 和 Seata，拆分为网关、用户、菜单、订单、取餐排队五个服务。部署方面支持 Docker Compose 启动基础组件，也支持 K3d/K3s 部署应用服务。

如果要概括项目的技术重点，我会强调四点：第一，使用网关统一完成 JWT 鉴权、角色校验和限流；第二，订单创建时使用 Seata 处理订单落库与库存预占的一致性；第三，使用 RocketMQ 延迟消息加定时扫描兜底处理订单超时；第四，使用 Redis 队列缓存和 WebSocket 推送支持食堂大屏实时叫号。

问：这个项目解决了什么实际问题？

答：传统食堂的主要问题是高峰期集中排队、用户无法提前知道菜品是否售罄、商家缺少结构化订单看板、出餐后需要人工呼喊且容易遗漏。这个项目将流程线上化：用户提前浏览当前可售菜单并下单，系统预占库存避免超卖；商家在订单看板中处理订单；出餐后系统自动将订单转入待取餐队列并推送叫号；用户可以通过二维码或取餐码完成核销。这样可以减少无效等待，并保留订单、库存、叫号和核销记录，便于追踪。

问：系统有哪些角色？每个角色能做什么？

答：系统有三种登录角色和一个展示终端。

用户 `USER` 可以注册登录、查看可售菜单、加入购物车、创建订单、支付、取消符合条件的订单、查看订单状态、查看取餐排队位置和二维码。

商家 `MERCHANT` 对应一个食堂窗口，可以管理菜品分类、菜品、每日菜单和库存预警，也可以查看订单、接单、拒单、出餐、手动叫号和核销。

管理员 `ADMIN` 可以管理用户、商家和各服务的业务配置，例如支付超时时间、商家接单超时时间、用户接单后允许取消的窗口时间、取餐号重置规则。

大屏端不要求登录，按窗口展示制作中队列、待取餐队列和叫号提醒。它属于公开展示终端，只展示取餐号，不展示用户隐私。

问：这个项目最值得讲的业务闭环是什么？

答：最值得讲的是一次正常订单从创建到取餐完成的链路：

1. 用户从某个窗口选择菜品，前端生成幂等 Key 后调用订单创建接口。
2. 订单服务从菜单服务获取菜品快照，重新计算订单金额，不信任前端金额。
3. 订单服务写入订单和订单明细，然后调用菜单服务预占库存。创建订单方法使用 Seata 全局事务。
4. 用户输入支付密码。支付成功后，订单从 `PENDING_PAY` 变为 `PAID`，取餐服务生成类似 `A001` 的取餐号，并把订单放入制作中队列。
5. 商家接单后，订单进入 `PREPARING`。
6. 商家点击出餐后，取餐服务生成二维码，把订单从制作中队列迁移到待取餐队列，记录自动叫号事件，并通过 WebSocket 向大屏推送更新。
7. 商家扫码或输入取餐码核销。取餐服务调用订单服务把订单改为 `COMPLETED`，订单服务通知菜单服务确认消费预占库存，最后取餐服务移除待取餐队列项。

## 二、架构设计

问：为什么要拆成微服务，而不是写成一个单体应用？

答：这个项目使用微服务主要是为了学习和展示不同业务域之间的边界，而不是因为当前数据规模已经必须使用微服务。用户、菜单、订单和取餐排队的变化原因不同：用户服务关注认证和账号；菜单服务关注窗口、菜品和库存；订单服务关注交易状态机和超时；取餐服务关注队列、取餐号、二维码和实时推送。拆分后，每个服务有独立数据库，职责比较清晰。

但微服务也引入了额外复杂度，包括服务发现、远程调用失败、分布式事务、消息队列、部署和排障成本。如果是团队规模较小、业务仍在早期验证阶段，我会优先考虑模块化单体；如果需要展示微服务治理能力，或者后续各业务域有独立扩展需求，再进行拆分。当前项目属于教学场景下有意识的微服务实践。

问：后端具体拆分了哪些服务？

答：后端共有六个 Maven 模块，其中五个是可运行服务，一个是公共模块。

`gateway-service` 运行在 `9000` 端口，负责统一路由、跨域、JWT 鉴权、角色权限校验和限流。

`user-service` 运行在 `9001` 端口，负责注册、密码登录、验证码登录、Token 刷新、退出登录、用户资料、支付密码校验和管理员用户管理。

`menu-service` 运行在 `9002` 端口，负责商家、菜品分类、菜品、每日菜单、库存预占、库存释放、库存消费和库存预警。

`order-service` 运行在 `9003` 端口，负责订单创建、支付、取消、查询、商家接单、拒单、出餐、订单完成和超时取消。

`pickup-service` 运行在 `9004` 端口，负责取餐号、制作中队列、待取餐队列、叫号、二维码、核销和 WebSocket 推送。

`smart-canteen-common` 是公共模块，包含统一返回结构、分页结构、错误码、枚举、异常、JWT 工具、雪花 ID 工具和用户上下文。

问：请求从浏览器进入系统后是怎样流转的？

答：本地开发时，浏览器访问 Vite 开发服务器，Vite 将 `/api` 和 `/ws` 代理到 `gateway-service:9000`。K3s 部署后，请求先进入 Traefik Ingress：静态资源转到前端 Nginx，`/api` 和 `/ws` 转到 Gateway。Gateway 再根据路径把请求路由到对应服务，例如 `/api/order/**` 转到订单服务，`/api/menu/**` 转到菜单服务。

受保护请求会先经过网关过滤器。网关解析 JWT，检查 Token 类型、过期时间和 Redis 黑名单，再根据路径校验角色。校验通过后，网关移除客户端可能伪造的用户请求头，并重新写入可信的用户 ID、角色和用户名。下游服务通过拦截器把这些请求头转换为线程内的 `UserContext`。

问：Nacos 在项目中做什么？

答：Nacos 用于服务注册发现和配置接入。每个微服务启动后注册到 Nacos，Gateway 和 OpenFeign 可以通过逻辑服务名调用实例，例如 `lb://order-service`。这样不需要在代码中写死业务服务 IP 和端口，也便于后续增加实例。项目还引入了 Nacos Config 依赖和 `bootstrap.yml`，为集中管理配置留出了入口。

问：服务之间如何通信？

答：同步调用主要使用 OpenFeign。例如订单服务调用菜单服务获取菜单快照、预占库存、释放库存和确认消费；订单服务调用用户服务验证支付密码；订单服务调用取餐服务进入制作队列或待取餐队列；取餐服务核销后调用订单服务完成订单。

异步通信目前主要用于订单超时。订单创建后，订单服务向 RocketMQ 发送支付超时延迟消息；订单支付后，再发送接单超时延迟消息。消费者收到消息后会读取数据库当前状态，只有仍处于目标状态且确实超时才执行取消，因此消息重复到达不会直接造成错误状态流转。

问：为什么有 `smart-canteen-common` 公共模块？

答：公共模块避免每个服务重复定义基础协议。项目中统一使用 `Result` 和 `PageResult` 返回结果，统一使用 `ErrorCode` 表达错误，订单状态、角色、餐段、库存变更类型等枚举也集中管理。JWT 签发和解析、雪花 ID、营业时间判断、用户上下文都放在公共模块。这样跨服务语义一致，减少接口联调时的歧义。

## 三、认证、权限与安全

问：系统登录认证是如何实现的？

答：用户服务支持密码登录和验证码登录。密码登录时使用 BCrypt 校验登录密码哈希；验证码登录时从 Redis 读取验证码并校验。登录成功后，用户服务签发 Access Token 和 Refresh Token。

Access Token 用于访问业务接口，Gateway 会解析它并校验角色。Refresh Token 用于换取新的令牌对。Refresh Token 的 JTI 会同时写入 MySQL 和 Redis，刷新时会检查数据库状态、有效期和 Redis 中当前有效 JTI。刷新后旧 Refresh Token 会被置为失效，旧 Access Token 会进入 Redis 黑名单，从而实现 Token 轮换。

问：为什么同时使用 Access Token 和 Refresh Token？

答：Access Token 适合设置较短有效期，用于无状态访问业务接口；Refresh Token 有效期更长，只用于换取新的令牌。这样兼顾安全性和用户体验。如果 Access Token 泄露，风险窗口相对较短；如果用户仍持有合法 Refresh Token，前端可以无感刷新，不必频繁重新登录。

前端 Axios 响应拦截器在遇到 `401` 时会自动刷新 Token。为了避免多个并发请求同时刷新，代码使用 `isRefreshing` 和等待队列：第一个失败请求发起刷新，其他失败请求暂存，刷新成功后统一重试。

问：退出登录之后，JWT 不是仍然可以使用吗？

答：纯 JWT 确实存在这个问题，因为签发后服务端默认无法主动撤销。项目在退出登录和刷新 Token 时把旧 Access Token 的 JTI 写入 Redis 黑名单，并设置剩余有效期作为 TTL。Gateway 每次鉴权都会检查 `token:blacklist:{jti}`。这样旧 Token 在有效期结束前也会被拒绝。

问：如何防止客户端伪造用户 ID 或角色请求头？

答：Gateway 不会直接相信客户端传入的用户上下文头。对于公开接口，网关会移除用户 ID、角色和用户名请求头；对于受保护接口，网关也会先移除这些头，再根据已经校验过的 JWT 重新写入可信头。下游服务只读取网关注入的值。部署时还应避免业务服务直接暴露公网，只让外部流量经过 Gateway。

问：角色权限在哪里控制？

答：第一层在 Gateway。网关根据 URL 模式控制角色，例如 `/api/admin/**` 只允许管理员，`/api/order/merchant/**`、`/api/menu/dishes/**`、`/api/pickup/call` 和 `/api/pickup/verify` 等接口只允许商家。

第二层在业务服务。服务不会只依赖 URL 权限，例如商家处理订单时，还会根据当前商家账号查询对应窗口，并验证该订单是否属于当前窗口。这样即使某个请求绕过网关或路径规则配置错误，也降低了越权操作风险。

问：网关限流是如何实现的？

答：Gateway 有一个全局限流过滤器，按 IP、用户和敏感接口分别限流。默认配置中，IP 限流额度为 `100`，用户限流额度为 `50`，敏感接口额度为 `5`。敏感接口包括发送验证码、注册、登录、刷新 Token、支付和取餐核销。

底层使用 Redis Lua 脚本实现令牌桶。Lua 脚本一次性完成读取桶状态、根据经过时间补充令牌、判断是否允许请求、扣减令牌和设置过期时间。Redis 中脚本执行具有原子性，避免多个网关实例并发更新桶状态时出现竞态。

问：支付密码安全吗？

答：当前版本中的登录密码使用 BCrypt 哈希存储，但模拟支付密码仍是明文存储和明文比对。这是为了简化教学演示，不符合生产系统安全要求。当前实现额外做了 Redis 错误次数限制：30 分钟内连续错误达到 5 次后锁定 30 分钟。

如果用于真实环境，我会把支付密码独立加盐哈希存储，使用恒定时间比较，限制错误次数和设备风险，避免在日志中记录敏感信息，并使用 HTTPS 传输。涉及真实资金时，还需要接入支付机构，而不是自己保存支付密码。

问：短信验证码是真的发送吗？

答：当前不是。为了便于本地演示，验证码固定为 `123456`，存入 Redis 后有效期为 5 分钟，同一手机号 1 分钟内只能发送一次。生产环境需要接入短信供应商，使用随机验证码，不应该在接口响应中返回验证码，还要增加图形验证码、设备风控、IP 限制和更细粒度的审计。

## 四、订单、库存与一致性

问：订单状态有哪些？状态机如何流转？

答：订单共有六种状态：

`PENDING_PAY` 表示待支付；`PAID` 表示已支付、等待商家处理；`PREPARING` 表示商家已接单并制作中；`READY` 表示已出餐、等待取餐；`COMPLETED` 表示已核销取餐；`CANCELLED` 表示已取消。

正常路径是：

`PENDING_PAY -> PAID -> PREPARING -> READY -> COMPLETED`

取消路径包括：

`PENDING_PAY -> CANCELLED`

`PAID -> CANCELLED`

`PREPARING -> CANCELLED`

其中制作中的订单只有在商家接单后的可取消窗口内才能由用户取消，默认窗口为 1 分钟。每次关键状态变更都会写入 `order_status_log`，记录原状态、目标状态、操作者、角色、备注和时间。

问：创建订单时为什么不能相信前端传来的价格？

答：前端数据可以被篡改，所以创建订单时前端只提交窗口 ID、每日菜单项 ID 和数量。订单服务调用菜单服务查询当前菜单快照，拿到真实的菜品 ID、名称、图片和价格，并在后端重新计算小计和总金额。订单明细中会保存下单时快照，避免商家后续改价或修改菜名后影响历史订单展示。

问：如何避免库存超卖？

答：库存扣减不是先查库存再更新，而是使用带条件的原子 SQL：

```sql
UPDATE daily_menu_item
SET reserved_stock = reserved_stock + #{quantity},
    remaining_stock = remaining_stock - #{quantity}
WHERE id = #{id}
  AND remaining_stock >= #{quantity}
```

如果受影响行数为 `0`，说明库存不足，业务抛出异常。数据库在一条 SQL 中完成条件判断和更新，可以避免多个并发请求先读到相同库存再分别扣减导致超卖。

问：为什么库存分成 `remaining_stock` 和 `reserved_stock`？

答：用户创建订单时还没有支付，但系统必须暂时锁住库存，否则多个用户都能下单占用同一份库存。因此创建订单时将库存从 `remaining_stock` 转移到 `reserved_stock`，这叫预占。

如果订单取消或超时，调用 `release`，把预占库存恢复到剩余库存。

如果用户最终核销取餐，调用 `consume`，减少预占库存，不再恢复到剩余库存。

这比创建订单时直接永久扣减更准确，也便于区分“已售出”和“暂时被待支付订单占用”。

问：创建订单时如何保证订单和库存的一致性？

答：订单创建方法同时使用本地事务 `@Transactional` 和 Seata 的 `@GlobalTransactional`。方法先写订单主表和订单明细，再通过 Feign 调用菜单服务预占库存。菜单服务库存预占也在本地事务中执行。Seata 使用 AT 模式，通过各数据库中的 `undo_log` 记录回滚信息。

如果库存不足，或者库存服务调用失败，创建订单的全局事务会回滚，避免出现“订单已创建但库存没有预占”或“库存已预占但订单没有成功创建”的情况。

问：为什么项目中使用 Seata AT 模式？

答：AT 模式对业务代码侵入较小，适合当前 MySQL 场景。业务仍然使用普通 SQL 和本地事务，Seata 通过数据源代理记录前后镜像，并在全局事务失败时利用 `undo_log` 回滚。

它的代价是依赖数据库事务、需要维护 Seata Server 和 `undo_log`，高并发下也要关注锁冲突和性能。对于更复杂的长事务，可能会选择 TCC、Saga 或基于消息的最终一致性方案。

问：创建订单如何防止重复提交？

答：前端创建订单时会携带 `X-Idempotent-Key`。订单服务把用户 ID、幂等 Key 和请求体的 SHA-256 摘要关联起来，成功提交事务后写入 Redis，TTL 为 30 分钟。

如果用户使用同一个 Key 重复提交相同请求，服务会返回原订单；如果同一个 Key 对应不同请求体，则返回重复提交错误。用户 ID 参与 Redis Key，可以防止不同用户之间互相影响。

需要说明的是，当前实现更适合防止用户重复点击和网络重试，并不是严格意义上的并发互斥：它采用“先查询、提交后写 Redis”的方式，两个完全并发的首次请求仍有小概率同时穿透。生产化改进可以使用 Redis `SET NX` 先抢占处理中状态，或者增加数据库唯一键，把幂等性下沉到持久层。

问：订单 ID 为什么使用雪花算法？

答：微服务环境下不适合依赖单库自增 ID，因为多个实例或多个库之间难以协调。雪花算法可以在本地快速生成大致有序的 64 位 ID，不需要每次访问数据库。项目中订单 ID 同时作为订单号字符串使用，其他需要业务侧生成 ID 的实体也可以复用公共工具。

前端处理 Java `Long` 时要注意 JavaScript 安全整数范围。项目中已经有订单 ID 序列化测试，实际接口应优先把长整型 ID 作为字符串返回，避免精度丢失。

问：订单超时是怎么实现的？

答：项目采用“双保险”机制。

第一层是 RocketMQ 延迟消息。创建订单后发送 `pay_timeout` 延迟消息；支付成功后发送 `accept_timeout` 延迟消息。消息到达后，消费者再次查询数据库当前状态，并检查时间是否真的超过配置阈值。这样已支付、已接单或已取消的订单不会被误处理。

第二层是定时扫描兜底。订单服务每 60 秒扫描最多 100 条超时的待支付订单和已支付未接单订单。扫描任务使用 Redis 锁 `lock:order:timeout-scan`，避免多实例重复执行。

这样即使消息发送、投递或消费暂时失败，定时任务也能补偿。

问：用户可以在什么情况下取消订单？

答：待支付 `PENDING_PAY` 和已支付待接单 `PAID` 状态可以取消。商家已接单进入 `PREPARING` 后，用户仍有一个有限取消窗口，默认是接单后 1 分钟。超过这个窗口后不能取消，避免商家已经投入制作却被随意撤单。取消时系统会恢复预占库存；如果订单已经进入制作中队列，还会从取餐队列中移除。

问：商家拒单会发生什么？

答：商家只能拒绝属于自己窗口且处于 `PAID` 状态的订单。拒单后订单变为 `CANCELLED`，写入取消原因和状态日志，并释放预占库存。如果订单超过接单时限仍未处理，系统也会自动取消，逻辑与拒单类似。

问：库存日志有什么作用？

答：菜单服务的 `inventory_log` 会记录 `RESET`、`RESERVE`、`RELEASE` 和 `CONSUME` 四种变更类型，以及变更数量、变更前后剩余库存、关联订单和时间。它便于排查库存异常，也可以支持后续做审计和报表。

对于释放和消费操作，服务会先检查该订单是否已有对应类型日志，避免重复调用造成重复恢复或重复消费。这是一种业务幂等保护。

## 五、取餐排队、叫号与实时推送

问：支付成功后为什么马上生成取餐号？

答：用户支付成功后就需要知道自己在窗口的排队标识，因此订单服务调用取餐服务进入制作中队列，并返回类似 `A001` 的取餐号。商家出餐后，这个取餐号会从制作中队列迁移到待取餐队列，用户和大屏看到的是同一个号码。

问：取餐号是如何生成的？

答：取餐服务使用 `pickup_number_sequence` 表保存当前字母和数字。号码格式是一个字母加三位数字，例如 `A001`。数字从 `001` 递增到 `999`，然后字母从 `A` 递增到 `Z`，到 `Z999` 后回到 `A001`。

生成号码前使用 Redis 分布式锁 `lock:pickup_seq`，锁值是随机 UUID，有效期 3 秒。释放锁时使用 Lua 脚本比较锁值后删除，避免误删其他实例后来获得的锁。序列表还支持 `NONE`、`DAILY` 和 `WEEKLY` 重置规则。

问：为什么队列既存 MySQL 又存 Redis？

答：MySQL 是真实数据源，保存制作中队列和待取餐队列，便于持久化和恢复；Redis 保存按窗口组织的列表缓存，提升大屏查询性能。队列变化后，服务会根据数据库重建对应 Redis 列表。读取缓存时如果不存在，也会从数据库重建。

这种设计保证 Redis 丢失后仍可以自愈。当前实现偏向简单可靠，而不是极致性能：每次队列变化后会重建列表。数据规模增大后，可以改为更细粒度的增量更新，或者使用 Redis Sorted Set。

问：自动叫号和手动叫号有什么区别？

答：商家点击出餐后，订单从制作中队列进入待取餐队列，系统会自动记录一条 `AUTO` 类型叫号事件并通过 WebSocket 推送 `CALL_NOTIFY`。如果用户没有及时取餐，商家还可以手动再次叫号，系统记录 `MANUAL` 类型事件并再次推送。历史叫号事件保存在 `call_event` 表中，大屏快照会返回最近 30 条。

问：大屏实时更新是如何实现的？

答：大屏通过 `/ws/screen/{merchantId}` 与取餐服务建立 WebSocket 连接。取餐服务按窗口 ID 维护会话集合。当制作中队列、待取餐队列或叫号事件变化时，服务向该窗口所有已连接大屏推送消息。

主要消息类型有：

`PREPARING_UPDATE`：更新制作中列表。

`WAITING_UPDATE`：更新待取餐列表。

`CALL_NOTIFY`：通知某个取餐号被叫号。

前端断线后会指数退避重连，最多尝试 10 次，最长等待 30 秒。如果仍然无法恢复，就进入轮询模式，每 10 秒请求一次快照接口。这保证 WebSocket 临时不可用时，大屏仍能继续更新。

问：二维码核销流程是怎样的？

答：商家出餐时，取餐服务为订单生成一个随机 32 位取餐码，并把订单 ID 和取餐码序列化为二维码内容。用户取餐时，商家可以扫码，也可以手动输入取餐码。

核销时，取餐服务会检查二维码是否存在、是否已核销、订单是否仍在待取餐队列、窗口是否匹配。校验通过后先调用订单服务完成订单；订单服务确认消费预占库存并把订单改为 `COMPLETED`。然后取餐服务标记二维码已核销、删除待取餐队列项、写入核销记录并推送大屏更新。

问：如何防止重复核销和错窗口核销？

答：二维码表中有 `is_verified` 标记，已经核销的二维码再次使用会被拒绝。核销时还会根据订单查询待取餐队列项，并校验队列项中的窗口 ID 是否等于当前请求窗口 ID。如果不一致，会返回错窗口错误。数据库中 `pickup_qrcode.order_id` 和 `pickup_code` 都有唯一索引，减少重复数据。

## 六、数据库设计

问：为什么每个微服务使用独立数据库？

答：项目按照业务域拆分为 `canteen_user`、`canteen_menu`、`canteen_order` 和 `canteen_pickup`。独立数据库使每个服务拥有自己的数据边界，其他服务不能随意直接查询其表结构，跨域访问通过接口完成。这可以降低耦合，也更符合微服务独立演进的原则。

代价是跨库事务和联表查询变复杂，所以项目使用 Seata 处理创建订单的跨服务一致性，用 Feign 获取快照或同步状态。统计报表如果变复杂，可以后续通过消息同步到专门的数据分析库。

问：核心数据表有哪些？

答：用户域有 `user`、`login_log`、`refresh_token`。

菜单域有 `merchant`、`dish_category`、`dish`、`daily_menu`、`daily_menu_item`、`inventory_log` 和 `config`。

订单域有 `order`、`order_item`、`order_status_log` 和 `config`。

取餐域有 `pickup_number_sequence`、`pickup_qrcode`、`preparing_queue_item`、`waiting_queue_item`、`call_event`、`verify_record` 和 `config`。

此外，Seata AT 模式需要在相关数据库中维护 `undo_log`。

问：为什么订单明细要保存菜品快照？

答：菜品名称、图片和价格可能在用户下单后发生变化。如果订单详情每次都读取菜单服务当前数据，那么历史订单会被后续修改影响，甚至出现结算金额无法解释的问题。因此 `order_item` 保存 `dish_name`、`dish_image`、`unit_price`、`quantity` 和 `subtotal`，确保历史订单可追溯。

问：数据库中为什么设计了配置表？

答：部分业务规则不适合硬编码，例如支付超时、商家接单超时、接单后取消窗口、取餐号重置规则和库存预警扫描间隔。各业务服务保留自己的 `config` 表，管理员可以通过接口修改。部分配置服务还会把值同步到 Redis，降低频繁读库成本。

问：项目中有哪些重要索引或约束？

答：用户表对用户名、手机号和学工号建立唯一索引；订单表对订单号建立唯一索引，并对用户加状态、商家加状态、创建时间和取餐号建立索引；二维码表对订单 ID 和取餐码建立唯一索引；制作中队列和待取餐队列都对订单 ID 建立唯一索引；每日菜单项对菜单 ID 和菜品 ID 建立组合唯一索引。

另外，SQL 中使用 `CHECK` 约束限制角色、状态、金额、库存和队列位置。即使业务代码出现问题，数据库仍能拒绝明显非法数据。

## 七、前端设计

问：前端为什么做成四个入口，而不是一个页面里切换角色？

答：四类终端使用场景差异较大。用户端面向手机；商家端偏平板或操作台；管理员端偏桌面管理后台；大屏端是展示终端。项目使用 Vite 多页面构建，入口分别是 `index.html`、`merchant.html`、`admin.html` 和 `screen.html`。它们共享公共 API、认证 Store、工具和组合式函数，但保留各自路由和页面结构。

这样既避免维护四套完全独立工程，也能让不同终端按需加载自己的页面代码。

问：Pinia 在项目中用来做什么？

答：公共认证状态使用 Pinia 管理，包括 Access Token、Refresh Token、用户资料和角色。用户端购物车也使用独立 Store 管理，包括菜品数量、窗口、总价和购物车弹层状态。

购物车限制一次只购买一个窗口的菜品。如果切换窗口且购物车不为空，会清空原购物车。这和后端订单结构一致，因为一个订单只对应一个商家窗口。

问：Axios 做了哪些统一处理？

答：Axios 实例统一设置 `/api` 基础路径和 15 秒超时。请求拦截器自动附加 Bearer Token，并在存在时附加 `X-Idempotent-Key`。响应拦截器统一解包后端 `Result`，遇到业务错误时抛出可展示的错误消息。

遇到 `401` 时，拦截器会使用 Refresh Token 换取新令牌并重试原请求。并发请求刷新时会进入等待队列，避免重复刷新。如果刷新失败，就清除本地 Token 并跳转登录页。

问：为什么大屏 WebSocket 还需要轮询兜底？

答：WebSocket 适合低延迟推送，但真实网络环境中可能断线，代理配置也可能临时异常。如果只有 WebSocket，大屏断线后会停止更新。因此前端在重连多次失败后，每 10 秒查询一次快照，保证最终能恢复数据。WebSocket 恢复后再停止轮询，减少不必要请求。

## 八、部署、测试与工程化

问：项目如何部署？

答：本地开发可以用 Docker Compose 启动 MySQL、Redis、Nacos、RocketMQ 和 Seata，再分别启动五个 Spring Boot 服务和 Vite 前端。

项目还提供混合部署方案：基础组件继续由 Docker Compose 运行，应用服务部署到本机 K3d/K3s 集群。Kubernetes 中包含 Namespace、Secret、ConfigMap、各服务 Deployment 和 Service、前端 Nginx，以及 Traefik Ingress。Ingress 将 `/api` 和 `/ws` 转给 Gateway，将 `/` 转给前端 Nginx。

问：为什么基础组件用 Docker Compose，而应用服务用 K3s？

答：这是面向本地学习和演示的折中方案。MySQL、Redis、Nacos、RocketMQ 和 Seata 状态较重，直接用 Compose 启动更简单；应用服务适合在 K3s 中练习容器编排、Service、Ingress、ConfigMap 和 Secret。这样既能展示 Kubernetes 部署能力，也不会把本地环境复杂度推得过高。

真实生产环境中，基础组件通常会使用云托管服务或独立高可用集群，不会只运行单实例 Compose 容器。

问：项目中 Redis 用在哪些地方？

答：Redis 有多个用途：

1. 保存短信验证码和一分钟发送频率限制。
2. 保存当前有效 Refresh Token JTI 和 Access Token 黑名单。
3. 保存支付密码错误次数和锁定状态。
4. 保存创建订单幂等记录。
5. 保存制作中队列和待取餐队列缓存。
6. 保存取餐号生成分布式锁。
7. 保存订单超时扫描任务锁。
8. 保存网关令牌桶限流状态。
9. 缓存部分管理员业务配置。

问：项目中 RocketMQ 用在哪些地方？

答：RocketMQ 目前聚焦订单超时。订单创建后发送支付超时延迟消息，订单支付后发送接单超时延迟消息。消息使用 `order-timeout` Topic，通过 `pay_timeout` 和 `accept_timeout` Tag 区分类型。消费者收到消息后再查数据库状态和时间，避免过期消息误取消已经推进的订单。

问：项目测试做到了什么程度？

答：仓库中后端共有 46 个测试文件，覆盖公共模块、网关、用户、菜单、订单和取餐服务。其中包括 JWT、雪花 ID、营业时间、网关鉴权、网关限流、Redis 令牌桶、登录、管理员用户管理、菜品、每日菜单、库存、菜单快照、订单创建、支付、取消、超时、幂等、RocketMQ 延迟消息、取餐号、队列缓存、核销和控制器集成测试。

父 POM 配置了 JaCoCo，在执行 Maven 测试后可以生成覆盖率报告。前端当前没有配置自动化单元测试脚本，这是后续应补充的部分。进一步完善时，我会增加 Testcontainers 或独立测试环境中的跨服务集成测试，并加入端到端测试覆盖正常下单取餐、超时取消、拒单和重复核销。

问：项目如何做可观测性？

答：当前每个服务暴露 Actuator 的 `health` 和 `info` 端点，部署文档中也提供了检查脚本。业务层保留登录日志、订单状态日志、库存日志、叫号事件和核销记录，这些对排查业务问题很有帮助。

如果进一步生产化，我会接入统一日志采集、Trace ID、分布式链路追踪、Prometheus 指标和 Grafana 看板，并为 MQ 堆积、接口错误率、库存异常、WebSocket 连接数和超时订单数量配置告警。

## 九、高频追问与改进方向

问：这个项目目前有哪些不足？请不要只说优点。

答：当前版本能够演示完整链路，但仍有明确的生产化改进空间：

第一，验证码仍是固定值并直接返回，只适合演示，需要接入短信服务和风控。

第二，模拟支付密码是明文存储，需要改为加盐哈希；真实支付应接入支付机构。

第三，订单幂等可以防重复点击和重试，但首次并发提交仍可能穿透，需要增加 Redis `SET NX` 处理中状态或数据库唯一约束。

第四，WebSocket 会话保存在单个 `pickup-service` 实例的内存中。如果部署多个实例，需要结合 Redis Pub/Sub、RocketMQ 或专门的 WebSocket 网关做跨实例广播。

第五，支付、出餐和核销链路中仍有跨服务同步调用，没有全部纳入分布式事务。生产系统应使用事件、重试、补偿任务和幂等消费强化最终一致性。

第六，当前队列位置使用插入时的位置序号，删除队列项后不会自动压缩，用户看到的“前方人数”可能不够准确。可改为查询时按排序动态计算，或使用 Redis Sorted Set。

第七，二维码目前没有显式过期时间。可以增加有效期、签名和防重放策略。

第八，菜品图片存放在数据库 BLOB 中，演示简单，但规模增大后应迁移到对象存储，数据库只保存 URL。

问：如果让你继续优化，你最先做哪几件事？

答：我会按风险优先级处理：

1. 先修复安全边界：支付密码哈希化、随机验证码、HTTPS、敏感信息脱敏、内部接口访问控制。
2. 强化一致性：为订单幂等增加原子抢占；为支付、出餐、核销增加事件表、重试和补偿扫描；对远程调用设计明确的幂等键。
3. 改进多实例能力：WebSocket 跨实例广播、队列位置动态计算、缓存更新策略和热点窗口压测。
4. 完善测试和可观测性：跨服务集成测试、端到端测试、链路追踪、指标和告警。
5. 优化存储和部署：图片迁移对象存储，基础组件改为高可用或托管服务，Kubernetes 增加探针、资源限制和滚动发布策略。

问：Seata 是否解决了项目里所有一致性问题？

答：没有。当前 Seata 重点用于“订单创建加库存预占”这一条链路。它能解决该链路中订单数据库和菜单数据库的原子回滚问题，但不是所有跨服务操作都自动获得强一致性。

例如支付成功时，取餐服务先创建制作中队列，订单服务再更新为 `PAID`；核销时，取餐服务调用订单服务完成订单，再更新自己的二维码和队列。如果中间某一步失败，需要依赖事务回滚能力、接口幂等、重试和补偿机制进一步完善。面试时应明确区分“已经实现的全局事务范围”和“后续需要加强的最终一致性范围”。

问：WebSocket 多实例部署会有什么问题？

答：当前连接保存在每个 `pickup-service` 实例自己的 `ConcurrentHashMap` 中。如果队列变更请求落到实例 A，而某块大屏 WebSocket 连接在实例 B，实例 A 无法直接向 B 内存里的连接推送消息。

解决方案是把业务事件发布到共享通道，例如 Redis Pub/Sub、RocketMQ 或 Kafka。每个取餐服务实例订阅事件，再向本机连接推送。也可以单独拆分 WebSocket 网关，并考虑负载均衡的会话策略。

问：为什么核销流程仍然需要改进？

答：当前核销流程已经做了二维码状态校验、窗口校验、订单状态校验和数据库事务，但它跨越取餐服务、订单服务和菜单服务。任何网络抖动都可能产生“远端已经成功，本地收到超时”的不确定状态。

生产化方案可以为核销请求增加全链路幂等键；订单完成接口保持幂等；通过本地事件表或事务消息发布“订单已完成”事件；取餐服务根据事件确认二维码和队列状态；再增加定时补偿任务扫描不一致记录。核心思路是允许消息重复，但每一步都能安全重放。

问：如果高峰期订单量突然上升，系统可能在哪里遇到瓶颈？

答：首先是热门窗口的库存更新，因为同一菜单项会成为数据库热点行。其次是订单创建链路包含多次跨服务同步调用和 Seata 全局事务，会增加延迟。再次是队列缓存当前采用重建整个列表的方式，窗口队列很长时成本会上升。大屏推送也需要关注连接数和单实例内存。

可以通过压测定位瓶颈，再按需优化：限制单窗口并发、拆分热点、缩短全局事务范围、使用异步事件、Redis Sorted Set 增量维护队列、批量推送、水平扩容和增加监控告警。

问：为什么内部接口没有直接暴露在 Gateway 路由中？

答：内部接口例如 `/internal/menu/order/snapshot`、`/internal/order/{orderId}/complete` 只用于微服务之间调用，不应该提供给浏览器。Gateway 只路由 `/api/**` 和 `/ws/**`，不会把 `/internal/**` 暴露给公网。

不过生产环境还应进一步加强：通过 Kubernetes NetworkPolicy、服务网格 mTLS、内部签名或服务身份认证限制内部接口，不能只依赖“没有配置外部路由”。

问：你在这个项目中体现了哪些工程思维？

答：我认为主要体现在以下方面：

1. 按业务域拆分服务和数据库，明确数据归属。
2. 不信任前端金额，创建订单时获取菜单快照并重新计算。
3. 用条件更新避免库存超卖，用预占、释放和消费表达库存生命周期。
4. 用状态机和状态日志约束订单流转并保留审计记录。
5. 对超时订单使用延迟消息和定时扫描双保险。
6. 对 JWT 撤销、支付错误次数、限流、队列缓存、分布式锁和幂等记录合理使用 Redis。
7. 对实时推送设计断线重连和轮询兜底。
8. 对现有实现的边界保持清楚，不把教学演示实现包装成生产系统。

## 十、快速复习版

问：如果老师最后只允许你讲三个技术亮点，你讲什么？

答：我会讲三个最完整的点。

第一，订单创建与库存预占：后端重新计算金额，保存订单快照，使用条件更新避免超卖，再用 Seata AT 模式保证订单库和菜单库一致回滚。

第二，订单超时：RocketMQ 延迟消息处理待支付和待接单超时，消费者读取当前状态避免误取消，Redis 锁保护的定时扫描再做兜底。

第三，取餐叫号：支付后生成取餐号，出餐后迁移队列并自动叫号，Redis 缓存提高查询效率，WebSocket 推送大屏，断线后前端指数退避重连并降级轮询。

问：如果面试官让你一句话总结项目的不足和改进思路，你怎么说？

答：当前项目已经打通微服务点餐取餐闭环并展示了事务、消息、缓存和实时推送能力，但仍是教学演示版本；下一步会优先补齐敏感数据安全、严格幂等、跨服务最终一致性、WebSocket 多实例广播和端到端测试。

问：答辩时有哪些内容不能夸大？

答：不能说短信验证码已经接入真实供应商，当前只是固定演示码；不能说支付是第三方真实支付，当前只是模拟支付密码；不能说所有跨服务操作都有 Seata 强一致性，当前重点覆盖创建订单与库存预占；不能说 WebSocket 已经天然支持多实例，当前会话仍保存在单实例内存；不能说前后端都有完整自动化测试，当前后端测试较丰富，但前端还没有配置单元测试脚本。
